# Handoff Writer

Produce a `HANDOFF.md` that lets the next session — a different agent, no memory of this
one — start working in under two minutes.

The failure mode this skill prevents: a handoff that restates the conversation. The next
agent does not need a summary of what was said; it needs **the state of the world, the
decisions already made, and the single next action.**

## When to use

- The user asks to hand off, wrap up, or summarize context for a new session.
- Context is running low and the task is unfinished.
- Work will resume later, on another machine, or by another person.

Do **not** use it for a progress update to a human who was present (that is a status
message), or to replace a commit message or PR description.

## Workflow

### 1. Establish the reader

Before writing, fix three facts. Ask only for what you cannot infer:

1. **Who resumes** — a fresh agent with repo access, a colleague, or future-you?
2. **What "done" means** — the concrete finish line, in one sentence.
3. **Where they start** — the working directory, branch, or file that is the entry point.

If the user is vague, propose a one-sentence goal and ask them to confirm or correct it.
A wrong goal in the handoff is worse than no handoff.

### 2. Separate what is recoverable from what is not

Everything in `git log`, the README, and the code is recoverable — do not transcribe it.
The handoff carries only what a new session cannot reconstruct:

| Keep | Drop |
| --- | --- |
| Why a decision was made, and what was rejected | The diff itself |
| Non-obvious traps already hit ("the API returns 200 with an error body") | Play-by-play of the conversation |
| Environment facts (versions, flags, credentials **names**, not values) | Full command output |
| Where the work stopped, precisely | "We discussed several approaches" |
| Unverified assumptions that the next step depends on | Praise, mood, meta-commentary |

Rule of thumb: if the line could be regenerated by reading the repo, cut it.

### 3. Write the file

Scaffold a skeleton, then fill it in:

```bash
node scripts/new-handoff.mjs --title "Fix ingest retry loop" --out HANDOFF.md
```

Or write it directly using the annotated template in
[`references/handoff-template.md`](references/handoff-template.md). The section order
matters: goal → state → next action → everything else.

### 4. Make the next action executable

The `## Next action` section must be specific enough to start without a decision:

- Bad: "continue debugging the retry logic".
- Good: "run `npm test -- ingest` — 3 cases in `test/ingest.test.mjs:88-140` fail because
  `retryDelay()` ignores `attempt`; fix there, then re-run."

Include the command, the file and line, what was already tried, and what to try next.

### 5. Close the loop

End your turn with:

```markdown
Handoff written to HANDOFF.md (N lines). Next session: read HANDOFF.md first, then
<entry point>.
```

## Output contract

A single Markdown file at the path the user chose (default `./HANDOFF.md`), with these
sections in this order:

1. **Goal** — one sentence, and what "done" looks like.
2. **State** — what works, what does not, last verified command and its result.
3. **Next action** — numbered, executable, ≤ 5 items, first item startable immediately.
4. **Decisions** — chosen option, rejected alternatives, and the reason. Date them.
5. **Traps** — things that cost time and would cost it again.
6. **Map** — files and directories that matter, one line each, with why.
7. **Open questions** — what is unresolved, and who or what can resolve it.

Keep it under ~150 lines. A handoff nobody reads to the end is not a handoff.

## Hard rules

- **Never put secrets in a handoff.** Reference credentials by name and location
  ("token in `~/.config/x/credentials`"), never by value — handoffs get pasted into
  chats, issues, and other agents' contexts. If the user pastes a secret, replace it with
  `<REDACTED>` and tell them to rotate it.
- **No personal data.** Names of colleagues, customers, or internal-only URLs do not
  belong in a file that will be shared. See the repo's `docs/publishing-checklist.md`.
- **State uncertainty as uncertainty.** "Assumed X; unverified" is honest and actionable.
  "X" when you are guessing poisons the next session.
- **Absolute paths only for the entry point.** Otherwise use repo-relative paths; the next
  session may run on another machine.
- **Write in the user's language.** The file is read by humans too; match the conversation.
- **No fabricated status.** If you did not verify something, say so and say how to verify.

## Example

```markdown
# HANDOFF — Fix ingest retry loop

## Goal
Ingest retries must back off exponentially and stop after 5 attempts. Done = `npm test`
green and a manual run shows attempt gaps of 1s, 2s, 4s, 8s, 16s.

## State
- Works: parsing, validation, happy-path ingest. Last verified `npm test` → 41 pass.
- Broken: `test/ingest.test.mjs:88-140` (3 failures) — retries fire immediately.

## Next action
1. `npm test -- ingest` to confirm the 3 failures still reproduce.
2. Fix `retryDelay()` in `src/ingest/retry.ts:31` — it ignores `attempt`.
3. Re-run tests, then verify the gaps manually with `node scripts/replay.mjs`.

## Decisions
- 2026-11-06 — exponential backoff over fixed delay. Rejected fixed delay: the upstream
  rate-limits in bursts; fixed 5s still tripped it in staging.

## Traps
- Staging returns HTTP 200 with `{"error": ...}` on rate limit — check the body, not the status.

## Map
- `src/ingest/retry.ts` — retry policy, the bug lives here.
- `test/ingest.test.mjs` — the 3 failing cases.
- `scripts/replay.mjs` — manual replay harness, takes a fixture path.

## Open questions
- Should the 5-attempt cap be configurable per source? Unresolved; ask before hard-coding.
```
