# Skill RSI

把一个已有 skill 的正确性，从「依赖模型的自觉」变成「有结构、有工具、可检查、能迭代」。

用原指南的话说，目标是四件事：**结构清晰、工具可靠、结果可验证、能持续改进**。

它要治的病很具体：读起来挺清楚，大多数时候也能用，但**没有办法知道这一次到底做对没有**。

## 什么时候用

- 用户说某个 skill 不稳定、总漏步骤、两次产出不一致。
- 用户要求「改造 / 升级 / 加固 / 自迭代」某个 `SKILL.md`。
- 一个 skill 的要求全是散文，没有一条被真正检查过。
- 你在同一个 skill 上被纠正了第二次。

不适用：从零写新 skill（那是另一件事），或者行为没问题、只想改措辞。

## 工作流

### 第一步：先读，先诊断，先别改

读 `SKILL.md`，再读它引用的每一个文件（`references/`、`scripts/`、`assets/`）。按四个维度写一份
简短诊断：每段一句话现状，**结尾必须落到一个具体缺口**，而不是一串抱怨。

| 维度 | 要回答什么 |
| --- | --- |
| **工作地图** | 照着走能到一个明确的终点吗？在哪里分叉，分叉条件写下来了吗？ |
| **工具能力** | 哪些步骤是重复的、确定的、容易错的？已经有脚本了吗？ |
| **验证机制** | 今天凭什么判断它做对了？哪些要求只有文字、没有检查？ |
| **反馈机制** | 用户纠错之后，什么东西真的变了？同类错误还会再来吗？ |

每个维度的追问清单、常见反例、以及「缺口怎么才算具体」，见
[`references/diagnosis.md`](references/diagnosis.md)。

**不要一上来就重构。** 一份让用户意外的诊断，比一次没人要求的重构有用；原指南也是这个要求：
先读、先给诊断，不要立即大规模重构。

### 第二步：确认验收标准，每轮最多 3 个问题

只问文件回答不了的事。问之前先自己找答案——翻文档、翻 `git log`、翻之前的纠正记录。有推断就把
推断摆出来让对方纠正，别开开放式问题：

> 「我理解『好结果』是 X，依据是 A 和 B，对吗？」

值得花一轮问的只有这三件：

1. 好结果长什么样？哪些是必须满足，哪些只是偏好？
2. 最不能接受哪种错误？过去哪些问题反复出现过？
3. 哪些环节必须人工确认，哪些可以放心交给 agent 自动跑？

三条纪律：不要让用户重新解释已经写在文档里的信息；每轮不超过 3 个问题；拿到答案后并进诊断，
不要推倒重来。

### 第三步：只改诊断支撑得住的部分

四件事，按下面这个优先级做——越靠前越便宜，也越耐用：

1. **结构化**：把工作地图写出来——目标、有序步骤、输入输出、依赖关系、分支条件、验收条件。
   只在「地图暴露了洞」的地方重写文字，不要通篇润色。
2. **工具化**：把**既重复又确定**的步骤写成脚本。一个入口（`scripts/xxx.mjs`，带 `--help`），
   一套退出码约定。一次性的步骤不做工具——原指南说得很清楚，**不强制每个 skill 都写 CLI**，
   硬造的 CLI 只是多一个失败面。
3. **可验证**：把每一条「可检查的要求」变成命令。记录检查对象、命令、结果；内容一变，相关检查
   重跑。语气、审美、是否得体这类主观判断留给人工，**说清楚它没被自动检查**，而不是假装检查过。
4. **可改进**：留一份纠错记录。把每个错误升级成最便宜、最耐用的那个东西：回归样例优先，其次是
   检查，再次是工具，最后才是加规则。同时把「这一次的偏好」和「长期规则」分开——否则每出一次事
   就长一条规则，skill 迟早没法读。

### 第四步：测试、对比、交付

- 把 skill 已有的样例端到端跑一遍。没有样例就先造一个最小样例，再动行为，否则「改造前」是不可
  度量的。
- 拿同一个样例对比改造前后，**明确说出任何退步**，不要只报喜。
- **未经用户确认，不要覆盖原始文件或正式交付物。** 要么在副本上改，要么先给 diff 等确认。
- 交付时把四类状态分开写。混在一起写，就是「看着像对」变成「已验证」的那条路。

| 状态 | 含义 | 需要的证据 |
| --- | --- | --- |
| **自动验证通过** | 命令跑过且通过 | 命令 + 输出 |
| **AI 评估通过** | 你读了结果并做了判断 | 你看了什么、为什么这么判 |
| **人工确认通过** | 用户点头了 | 用户的原话 |
| **尚未验证** | 没有证据 | 不要偷偷升级成上面任何一类 |

交付报告模板在 [`references/report-template.md`](references/report-template.md)，四件事按顺序说：

1. 改了什么，为什么（对回诊断的哪一条）。
2. 现在什么能自动检查了，用哪条命令。
3. 什么仍然需要人判断。
4. 下一次纠错从哪个入口进来。

## 硬规则

- **没有证据，不许说验证通过。** 没有命令输出，就没有「已验证」。
- **不许靠加规则来灭火。** 如果最后只剩「加一条规则」这一条路，说明诊断错了——优先补样例或补检查。
- **不要重构已经能用的东西。** 丑但有效的设计先留着，风格不是目标。
- **不要动用户没指的 skill。** 如果证据表明兄弟 skill 有同样的病，先问。
- **不要顺手改 `description`。** 它是触发面，改它就等于改行为，要单独确认。
- **缺口补上就停。** 一个 skill 改完胖了 40%，那是警报，不是战果。

## 输出契约

按顺序给：诊断 → 确认过的标准 → 变更 → 四状态验证表 → 下一轮入口。**整份不超过 40 行。**

标准是：用户读完诊断就可以不看后面，也知道你准备干什么。

## 出处

四维框架、四类状态、以及「工具与样例优先于散文规则」这三条，来自 **《Skill 自迭代能力改造指南》**，
由 **晓辉博士 / 新可能实验室（NEW POSSIBILITIES）** 公开发布。

本文件是为 agent 直接执行而做的重新表达，**不是官方发布，也不代表作者背书**。
