# Skill RSI

## 使用方式

用户会给出需要改造的 Skill 路径；没给就先问。先阅读现有文件并提供简要诊断，再与用户确认标准，
最后实施改造。

## 改造目标

请帮我检查并改造现有 Skill，让它从一份依赖 AI 理解和执行的操作说明，逐渐变成一套：

- 结构清晰
- 工具可靠
- 结果可验证
- 能够根据反馈持续改进

的工作系统。请遵循以下步骤。

## 第一步：理解现有 Skill

先阅读 Skill 及其关联文件、脚本和参考样例，梳理：

1. **工作地图**（参考 Feature Map）：任务目标、执行步骤、输入输出、依赖关系、关键分支。
2. **工具能力**（参考 CLI）：哪些操作已经有工具支持？哪些重复、确定性的步骤值得封装成工具？
3. **验证机制**：目前如何判断任务完成、结果正确？哪些要求只有文字说明，没有实际检查？
4. **反馈机制**：用户指出错误后，如何修正？如何避免同类问题再次发生？

尽量保留已有的有效设计，不要为了重构而重构。

## 第二步：与用户确认验收标准

先根据现有 Skill 提出你理解的标准，再向用户确认。重点询问：

1. 好结果是什么样的？哪些要求必须满足，哪些只是偏好？
2. 最不能接受什么错误？过去有哪些反复出现的问题？
3. 哪些环节必须人工确认？哪些可以放心交给 Agent 自动执行？

交互要求：

- 优先从现有文档、历史反馈和样例中寻找答案。
- 只问缺失或模糊的关键问题，每轮最多 3 个。
- 不要让用户重新解释已有的信息。

## 第三步：实施改造

根据诊断结果，按需实施：

1. **结构化**：建立简洁的工作地图，让 Agent 理解任务、步骤、依赖和验收条件。
2. **工具化**：把重复、确定性的操作封装成可复用工具。需要时提供统一 CLI 入口，不强制所有
   Skill 都开发 CLI。
3. **可验证**：把明确要求转化成自动检查，记录检查对象、结果和证据。内容变化后，相关验证应
   重新执行；语义、审美等主观判断保留人工复核。
4. **可改进**：建立反馈记录，优先把错误转化为认可样例、程序检查或工具修复，必要时再更新
   Skill 说明。区分单次要求与长期规则，避免规则无限膨胀。

## 第四步：测试与交付

- 使用已有样例进行回归测试，条件允许时再增加真实任务测试。
- 对比改造前后的结果，确保原有重要功能没有退化。
- 未经用户确认，不覆盖重要原始文件或正式交付结果。
- 明确区分四类状态：① 自动验证通过 ② AI 评估通过 ③ 人工确认通过 ④ 尚未验证。

最后简要说明：

1. 改造了什么，为什么？
2. 哪些问题现在可以自动检查？
3. 哪些问题仍然需要人工判断？
4. 以后用户提出反馈时，如何进入下一轮改进？

## 核心原则

- 优先解决真实问题，不追求复杂架构。
- 优先修改工具、检查和好样例，而不是不断增加提示词。
- 没有证据，不宣称验证通过。

## 开始执行

请先阅读现有 Skill，给出简要诊断；不要立即大规模重构。

## 与原文的差异

原文是发给人看、由人复制给 Agent 的指南；这里改成可直接加载的 SKILL.md，只动了三处：

1. 删掉「将本指南完整复制给 Agent」的投递说明——skill 被加载时就已就位，这层没有对应动作。
2. 「使用方式」里「告诉它需要改造的 Skill 路径」保留为第一句：没给路径就先问。
3. 补了 SKILL.md 必需的 frontmatter，以及末尾一段出处说明；其余原文照搬。
