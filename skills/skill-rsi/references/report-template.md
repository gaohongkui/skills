# 交付报告模板

第四步交付时读这份。整份控制在 40 行以内——用户读完诊断就能不看后面，也知道你干了什么。

```markdown
## 诊断
- 工作地图：<现状> — 缺口：<文件:行>
- 工具能力：<现状> — 缺口：<文件:行>
- 验证机制：<现状> — 缺口：<文件:行>
- 反馈机制：<现状> — 缺口：<文件:行>
- 结论：<最弱的一环> → <能补上它的最小改动>

## 确认过的标准
- 必须满足：<来自对话>
- 不能出现：<来自对话>
- 必须人工确认：<来自对话>

## 改了什么
- <文件>：<改动> —— 对应诊断第 <N> 条
- <文件>：<改动> —— 对应诊断第 <N> 条

## 验证
| 检查项 | 状态 | 证据 |
| --- | --- | --- |
| <做了什么> | 自动验证通过 | `<命令>` → <结果> |
| <做了什么> | AI 评估通过 | 读了 <产物>；<判断> |
| <做了什么> | 人工确认通过 | 用户原话：「<原话>」 |
| <做了什么> | 尚未验证 | 需要 <什么> |

## 还需要人判断的
- <你故意没有自动化的那个判断>

## 下一轮
- 下次纠错：记到 <位置> → 升级成 <样例 / 检查 / 工具>
```

## 填表规矩

- **验证**表每一行，第三列都必须有证据。证据格空着，状态就是「尚未验证」，标签写什么都不算。
- **AI 评估通过**不是「验证通过」的委婉说法。写清你看了什么，用户才有机会不同意你的判断。
- **人工确认通过**要引用用户原话。你自己概括的「用户认可了」不算。
- 有退步就写进「改了什么」，别省。说「没有退步」时，你得能指到一条命令。
- 如果什么都没改，就照实说。一次干净的诊断也是合格交付，而且比一次没补上任何缺口的重构便宜。
