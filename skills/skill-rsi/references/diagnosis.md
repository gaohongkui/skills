# 诊断：四个维度怎么查

第一步写诊断时读这份。四个维度，**每个只落一个具体缺口**。

什么叫具体？缺口要能指到一个文件、一个步骤、或一条不存在的命令。
「这个 skill 写得不够清楚」不算缺口，「第三步说『确保链接有效』，但没有跑任何链接检查」才算。

每个维度都先看证据，再提问。证据包括：文档、`git log`、`references/`、对话里过去的纠正、已有样例。

## 一、工作地图

要判断的是：一个没参与过的人，能不能照着走到明确的终点？

看这几处：

- **终点能不能观测**——「校验所有链接」可观测，「打磨得专业一点」不可观测。
- **步骤有没有序**——是编号步骤，还是散在散文里？有没有「必须先做 A 才能做 B」却没写的隐含依赖？
- **分叉条件在不在**——每个「如果用户想要 X，就做 Y」的条件，应该出现在触发面或步骤开头，
  而不是埋在第六步中间。
- **输入输出写没写**——skill 收到什么、产出什么具体文件。没写输出的 skill，永远无法验证。
- **依赖点名没有**——文件、CLI、网络、凭据，是写清楚了还是默认存在？

常见缺口：终点不可观测；只有作者知道的分支；输出用形容词描述（「一份好的总结」）。

## 二、工具能力

要判断的是：哪些步骤**既重复、又确定、又容易错**？

读的时候顺手填一张表：

| 步骤 | 重复？ | 确定？ | 易错？ | 已有脚本？ |
| --- | --- | --- | --- | --- |

只有前三列都是「是」，才值得写脚本。连着三个「否」，那是信号，不是待办。

值得注意的迹象：

- 同一串 shell 命令在散文里出现两次。
- 失败是静默的步骤：编码、路径分隔符、引号、换行。
- 模型在用眼睛做的检查，20 行脚本能做得一模一样。

**不要**脚本化：一次性迁移、需要判断力的环节、以及「脚本比它替代的那段文字还长」的东西。
原指南明确写了不强制 CLI；硬造的 CLI 只是多一个失败面。

## 三、验证机制

要判断的是：今天凭什么知道它做对了？

把每一条要求分成两类：

- **可检查**：文件存在、链接可解析、frontmatter 有某个键、命令退出码为 0、表格有 N 行、输出符合
  某个 schema、不含某个禁止字符串。
- **不可检查**：语气、审美、例子有没有说服力、建议是否明智。

然后回答：现在哪些「可检查的要求」是用散文写的承诺？每一条都是 skill 在赌模型自觉。要么把它变成
命令，要么明确标注「这项由人工复核」。

最典型的反模式：skill 里写着「确保链接都能打开」，但从来不跑链接检查。那句话是愿望，不是闸门。

## 四、反馈机制

要判断的是：用户纠错之后，什么东西真的变了？

看这几处：

- 同一个问题是否跨会话重复出现——**同一次漏两遍，说明上次的修复只是改了措辞**。
- 纠错过的案例有没有被留下来当样例。只活在聊天记录里的纠正，等于没有。
- 有没有地方放：`evals/`、`samples/`，或者 skill 自己的 `references/`。

动手之前先给纠正分类：

| 纠正内容 | 最便宜且耐用的修法 |
| --- | --- |
| 「输出结构不对」 | 加一个回归样例 |
| 「老是漏第三步」 | 补一条检查，或重排工作地图 |
| 「语气不对」 | 在 `references/` 里放一个范本 |
| 「这次我想短一点」 | 什么都不做——这是一次性偏好 |

最后一行最重要。把一次性偏好提升成长期规则，是 skill 变成天书的主要途径。

## 诊断怎么写

五行，一个维度一行，最后一行给结论：

```text
工作地图：<现状> — 缺口：<文件:行 或 步骤>
工具能力：<现状> — 缺口：...
验证机制：<现状> — 缺口：...
反馈机制：<现状> — 缺口：...
结论：<四者里最弱的一环>，建议先做<能补上它的最小改动>。
```

最后一行不是格式要求，是防身用的：它逼你**先挑一个改**，而不是四项一起动、改完看起来焕然一新却
什么都没验证。
